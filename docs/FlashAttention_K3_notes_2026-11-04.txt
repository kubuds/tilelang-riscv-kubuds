# 《FlashAttention 在 SpacemiT-K3 上的 Triton 实现》拆解与 K3 优化落地

日期：2026-11-04　原文：知乎 Alex，2026-10-14，27 页
实验环境：K3（8×X100 + 8×A100），spine-triton 3.6、torch 2.8

## 1. 文章做了什么

用 spine-triton 在 K3 上实现 FP16 FlashAttention（D=64/128，普通与 causal），两条路径：

- `smt block`：`smt.descriptor_load` / `smt.view` / `smt.dot`，矩阵 inner block 固定 16×32，外层 BM×BN 可调，8 个 program 跑在 A100（CPU8-15），Python 主线程在 X100（CPU0-7）。
- `smt_rvisa`（`tle.raw_kernel`）：自己控制 `tle.vpack` / `tle.vload` / `tle.vmadot` 与 FP32 累加器，把工作区放进 TCM。

最终数字（B=1，单 head，N=1024，D=64，普通）：PyTorch SDPA 309.73 ms，Triton **1.726 ms**；扫描分块后 64×128 到 1.615 ms。注意这两个数不是同一批核心：PyTorch 用 8 个 X100，Triton 用 8 个 A100。

## 2. 它真正的发现（这才是要拿走的东西）

### 2.1 收益不在矩阵乘里，在矩阵乘和 softmax 的衔接处

固定 32×64 外层块、同一份 raw kernel，只改数据布局，四组配置提升 5.37–7.40×：

| N=1024，单 head | 旧 TCM | 仅 V 转置打包 | 仅行布局 | 两者组合 | 倍数 |
|---|---:|---:|---:|---:|---:|
| D=64 普通 | 9.880 | 9.104 | 2.475 | **1.726** | 5.72× |
| D=64 causal | 6.259 | 5.838 | 1.528 | **1.167** | 5.37× |
| D=128 普通 | 14.096 | 12.604 | 3.474 | **1.904** | 7.40× |
| D=128 causal | 8.934 | 7.972 | 2.303 | **1.281** | 6.97× |

"行布局/64 lane" 是三件事合起来：矩阵结果按行连续存放（`vstore(..., row_stride=bn)`）、去掉窄读取的填充缓冲、把 64 个 lane 的归约一次做完。旧版一行分数被切成两个 32 宽片段，softmax 只能分片读，backend 还得构造 VL=2 的复制循环来补宽度；改成行连续后，一行 64 个元素一次 `vector<64xf32>` 归约完成。

### 2.2 不变的量要从循环里提出来

Q 在整个 KV 扫描期间不变，旧版每轮 KV 都重新打包一次。外提之后才有空间把外层块从 16×32 扩到 64×128。另一个例子是 `viota()`：64 个索引每行、每片段都重建，按 N=1024/BM32/BN64 的循环边界算是每个 query block 2048 次；挪到 query 初始化只做一次，单项就省 **8%**。

### 2.3 转置要融进生产者，不要单独走一遍

V 需要 [BN,D] → [D,BN]。旧版用标量循环，汇编里是 `flh`/`fsh` 一次搬一个元素（源地址 +128 B、目标 +2 B）。改成给 pack 加 `transpose=True`，直接对原 V 建 strides=[1,D] 的转置视图交给 `linalg.pack`，汇编变成 8 条 `vle16.v` 加 4 条 `smt.vpack.vv`。省掉的是 Vt 的一次写和一次读。

### 2.4 分块大小受任务数约束，不是越大越好

8 个 program 要都有活干。N=256、BM=64 时只有 4 个 query 任务，一半核心空转；同一形状 32×128 是 0.67 ms，64×128 反而 1.22 ms。N=1024 时 32×128 与 64×128 打平（8.71 / 8.72）。

### 2.5 causal 要前后交替派活

`task = pid + 8*t` 会让同一个 program 在各个 head 里反复领到同一位置：负载 8,8,16,16,24,24,32,32。改成前后交替后每个 program 都是 20。H=8、N=256、D=64 的 causal 从 6.81 ms 降到 4.35 ms（1.57×），普通模式不变（6.31 ms）。

### 2.6 TCM 不等于快

先把工作区搬进 TCM、分块不动：11.94 → **13.77 ms（更慢）**；把外层块扩到 32×128 让复用起来，才降到 8.71 ms。TCM 申请量 55,680 B（BM32/BN64/D64），扩块后 104,832 / 158,464 B，同时寄存器 spill 出现——容量和寄存器压力要一起看。

### 2.7 精度路径要显式

`smt.dot` 返回 FP16 块结果再 `arith.extf` 升 FP32，舍入在升精度之前就发生了。raw 路径能把 QKᵀ、PV 的块结果直接留在 FP32，只把送进矩阵单元的 p 转 FP16。

## 3. 映射到 K3 的三条栈

### 3.1 TileLang：布局 > 算力，但要在原位验证

本次按 2.2 的思路做了一个实验：把 M=8 预填 GEMV 的 K 切成 512 的块，让 8 行激活的切片常驻 L1，输出行在块内循环。孤立测量和原位测量结论相反：

| 形状 | 原内核 | K 分块内核 |
|---|---:|---:|
| N=2048 K=1024 | 16.4 GB/s | 5.1 GB/s |
| N=1024 K=3072 | 1.14 GB/s | **4.39 GB/s** |

K=3072（down_proj）确实从 1.14 提到 4.39 GB/s，但整链路预填反而从 629 ms 退化到 842 ms（20 token），实测后已回滚。原因是每次分块都会重开一个 OpenMP region（每层 6 个而不是 1 个），加上原位调用时 x 刚被 silu 写过、权重刚被上一层冲掉，和孤立基准里反复复用同一缓冲完全不同。

这条正好印证原文的测量纪律（预热、5 轮 ×10 次、轮内随机顺序、取中位数、p10–p90）：**孤立微基准只用来筛方向，结论必须回到原位**。

真正该沿用的两条：

- 输出布局按消费者写。我们的 M=8 内核把 8 行结果写回 `y[m*N+n]`，消费者（bias add、rope、silu_mul）按行读，已经是连续行；保持这个约定，不要为了归约方便改成 `[n][8]`。
- 减少每 token 的程序切换。8B 走逐层路径，每 token 36 次 launch + 36×7 次 GEMV 调用；原文用"一个 program 领一整块 query"的思路换成"一个 program 领多层"，就是 megakernel 方向。

### 3.2 vLLM：可以直接搬的两条

- **causal 负载均衡**（2.5）：PagedAttention 的 prefill 分块、chunked-prefill 的任务派发都是同一个背包问题；K3 只有 8 个可用核，负载不均衡的代价被放大。
- **分块受任务数约束**（2.4）：K3 上把 block 调大很容易把 8 个核喂不满，vLLM 的 `max_num_batched_tokens` / block size 调参要按核数对齐。

### 3.3 FlagOS / FlagGems：用 raw kernel 走 M=1 与融合路径

FlagGems 现有算子在 decode 形状（M=1）比 torch 慢 100 倍以上，问题正是"用通用 2D tile 写 GEMV"。原文的 raw 路径给了三个可复用的手法：

- `tle.vpack` + `tle.vmadot` 直接组织 16×32 inner block，FP32 累加器常驻，避免块结果降精度；
- 工作区进 TCM 前先确认复用够（2.6），否则别搬；
- 转置融进 pack（2.3），KV cache 的 `[pos][D]` → `[D][pos]` 视图可以直接交给 pack，不必先落一份转置副本。

## 4. 建议的执行顺序

| 优先级 | 动作 | 依据 | 预期 |
|---|---|---|---|
| P0 | 把"原位测量"写进流程：任何内核改动先跑孤立基准，再跑 0.6B/8B 端到端 | 本次 K 分块的反例 | 避免假收益 |
| P1 | 8B 的 megakernel / 多层融合，砍掉 36 次 launch | 2.2、2.4 | 8B 解码 1.95 → 2.5+ tok/s |
| P2 | decode GEMV 用 raw kernel 重写（M=1 特化，FP32 累加 + TCM） | 2.7、3.3 | GEMV 有效带宽 已 15.3 GB/s，空间在调用开销 |
| P3 | KV cache 改 `[D][pos]` 布局，attention 侧连续读 | 2.3 | 长上下文 attention 提升 |
| P4 | 若上 vLLM：causal 前后交替派活、block 按 8 核对齐 | 2.4、2.5 | prefill 1.5× 量级 |

## 5. 本次落地

- 新增 `gemv_q8_m8_kb`（K 分块 M=8 GEMV）与其基准 `testing/riscv/gemm/gemv_m8_kb.c`，**默认关闭**，保留作为 K=3072 的形状特化候选；
- 引擎回滚到已验证的 629 ms 预填 / 23.6 tok/s 解码路径；
- 结论写入技能库，后续内核改动一律先原位验证。
