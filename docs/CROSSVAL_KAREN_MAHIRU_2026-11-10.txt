# TileLang RISC-V：kubuds-riscv-karen / kubuds-riscv-mahiru 交叉验证与逐算子测评

日期：2026-11-10　　测试板：SpacemiT K3（Bianbu，8×X100 RVV VLEN=256 + 8×A100 IME2，31 GB）
对比基线：本仓库 `riscv-backend` 分支（int8 + RVV 自研引擎）

---

## 一、结论

两个分支走的是两条不同的路，都有可取之处，但**只有 mahiru 的路线能在 K3 上真正提速**：

| 项目 | karen | mahiru | 本次结论 |
|---|---|---|---|
| 主线 | 把 `T.gemm` 接到 cblas / RVV / IME2 运行时 ABI | 绕开 TileLang 算子层，用 vendor IME2 + Q4_0 直接跑整模型 | 两者可并存：算力型走 cblas，内存型走 IME2-Q4 |
| 可验证的量化收益 | cblas 512³ 76.28 GFLOP/s（官方文档） | 0.6B 41.7-45.9 tok/s、DS-1.5B 19.1 tok/s | **两条都复现成功** |
| 对本地引擎的贡献 | 修正我们用错线程数导致的 GEMM 低估（40.4 → 80.9） | 4bit + IME2 解码路线，**端到端 1.94×** | 已采纳 |

本次改动后本仓库的实测（K3，greedy，128 token KV）：

| 模型 | 权重 | 旧：int8 + RVV | 新：Q4_0 + IME2 | 提升 | 同板 llama.cpp |
|---|---:|---:|---:|---:|---:|
| Qwen3-0.6B | 0.65 GB | 23.80 tok/s | **44.12 / 46.37 tok/s**（两次） | 1.86-1.95× | 53.39（Q4_0，4 线程） |
| DeepSeek-R1-Distill-Qwen-1.5B | 1.35 GB | 8.40 tok/s | **16.34 tok/s** | 1.94× | 16.22（Q4_K_M，历史实测） |

0.6B 达到同板 llama.cpp 的 **87%**，1.5B 基本持平。两个模型的输出都通顺正确
（"Paris, and the capital of Italy is Rome…" / "Paris. Suppose we denote France as F, Paris as P"）。

## 二、karen：`T.gemm` 的三条 lower

### 2.1 它的做法

`tilelang/riscv/` 下自带 `target.py / blas.py / ime.py / pipeline.py / runtime.py / qemu.py`，
把 RISC-V 当成完整后端做：`T.gemm` 可以 lower 到 cblas、RVV 微内核或 IME2 运行时 ABI；
另有 QEMU 用户态挂具做无板测试（`src/riscv/harness`、`testing` 里的 QEMU 用例）。

值得借鉴的三点：

1. **cblas 卸载作为默认快路**。它在 TIR 里直接 `T.call_extern("cblas_sgemm")`，
   512³ 拿到 76.28 GFLOP/s。我们此前只把它当作"对照项"，没有当成生产路径。
2. **IME2 用稳定的运行时 ABI 抽象**：`spacemit_ime2_mma_i8/i16` 三个 C 符号，
   TIR 只认 ABI 不认指令编码。这比我们"把 `smt.vmadot` 内联汇编编进 `.so`"更容易移植
   （厂商指令编码非公开），代价是多一层调用。
3. **VLEN 感知的向量化宽度**：同一份 RVV 代码按 target 的 `vlen` 属性选 LMUL。

### 2.2 复现与差异

* cblas 76.28 GFLOP/s：**复现，且略高**。裸 cblas 512³ 实测 80.9 GFLOP/s
  （`OPENBLAS_NUM_THREADS=4`），numpy 路径 76.8，两者一致。
* 关键发现：**OpenBLAS 的线程池由 `OPENBLAS_NUM_THREADS` 决定，不读 `OMP_NUM_THREADS`**。
  我们之前记录的 `blas="openblas"` 只有 40.4 GFLOP/s，就是因为进程里 OMP 是 4 线程、
  OpenBLAS 自己按 8 核开池，超订后掉到 34.9（三次一致）。改成 `OPENBLAS_NUM_THREADS=4`
  就是 80.9。**这一条直接修正了我们文档里的一个错误数字。**
* IME2：karen 未给测速数字，其 ABI 与我们 `smt.vmadot` 内核驱动的是同一硬件，
  我们的裸内核 1024³ int8 是 840 GMAC/s、`max|err|=0`，可以作为它的上界参考。
* karen 的完整 tree 需要重新编 LLVM + TVM（数小时），本次没有整树构建，
  只验证了它公开的量化结论与机制。**这是本次测评的已知缺口。**

## 三、mahiru：Q4_0 + IME2 的整模型路线

### 3.1 它的做法

`riscv/{qwen_graph,ime2_bridge,ds1b_graph}.cpp` 三个文件，把 28 层 Qwen3-0.6B
写成一个 spert 图，一个 launch 跑完整个 decode；权重是 **Q4_0 → IME2 32×32 tile 重排**，
7 个 GEMV + attention + norm 全在 A100（4 worker）上。

它的账很干净：FFN 0.681 ms/层、lm_head 4.3 ms、28 层 19.7 ms + 4.3 = 24 ms，
即 41.7 tok/s 的预算上限。

### 3.2 复现结果

我们没有搬它的 spert 图，而是**把它的算子接进我们自己的 TIR 引擎**（这样才可维护）：

* `libime2bridge.so`：用它的 `ime2_bridge.cpp` + 板上已有的 vendor `ime2_kernels.o /
  rvv_kernels.o / repack.o` 编译（补一个 `main_kernel` 空桩解决链接）；
* 逐算子 microbench（Q4_0，N/K 为 0.6B 的真实形状，4 worker）：

| 形状 (N×K) | 时间 | 带宽 | 对应层内算子 |
|---|---:|---:|---|
| 1024×1024 | 0.031 ms | 19.26 GB/s | k_proj / v_proj |
| 1024×3072 | 0.090 ms | 19.64 GB/s | down_proj |
| 3072×1024 | 0.087 ms | 20.40 GB/s | gate / up |
| 4096×1024 | 0.113 ms | 20.94 GB/s | q_proj / o_proj |
| 151936×1024 | 4.016 ms | 21.79 GB/s | lm_head |

  对比我们的 int8 RVV GEMV：15.3 GB/s（X100，7 线程）。Q4 不但带宽更高，
  每个权重还只读 4.5 bit，**有效吞吐约为 2 倍**，这与端到端 1.94× 完全吻合。
* 端到端（我们的引擎，逐层 TIR，未做整图融合）：
  * Qwen3-0.6B **44.12 / 46.37 tok/s**（两次，它自报 41.7-45.9）
  * DS-R1-1.5B **16.34 tok/s**（它自报 19.1）
* 它的"单 launch 整图"并没有比我们的逐层 TIR 更快——说明瓶颈不在 launch 次数，
  而在每层那条依赖链。它自己的 step 24 也记了同样的结论（launch 合并无收益）。

### 3.3 采纳时踩到的两个坑（已修）

1. **KV 头数语义**：引擎的 `NKV` 是"存储的（补零后的）头数"，`nkv_attn` 是真实 GQA 组数。
   DS-1.5B 是 2 头补到 4，两个字段写反会让 attention 读错 kv 头 → 输出乱码。
2. **Qwen2 的 attention bias**：DS-1.5B 的 q/k/v 有 bias，且必须按
   `[bq | bk | bv]` 连续存放（k/v 补零到 4 头）。漏掉 bias 时输出是
   "www recommended bsp -quality…"，把它补上才通顺。

另外验证了量化器本身：自写 Q4_0 量化与 llama.cpp 逐字节一致
（同一个 tensor，`d` 和 16 个 nibble 全同，对 fp32 的相对误差都是 8.83%）。

## 四、逐算子对照（K3 实测汇总）

| 算子 / 场景 | 我们的 RVV（X100） | cblas（X100） | IME2（A100） | llama.cpp 同板 |
|---|---:|---:|---:|---:|
| fp32 GEMM 512³ | 29.2 GFLOP/s（4 线程） | **80.9**（4 线程） | — | — |
| int8 GEMM 1024³ | — | — | **840 GMAC/s**（裸内核） | — |
| Q4 GEMV 1024×1024 | 15.3 GB/s（int8） | — | **19.3 GB/s** | — |
| Q4 GEMV 151936×1024 | 22 GB/s（int8，head） | — | **21.8 GB/s** | — |
| 0.6B prefill | 25 ms/token（批量） | — | — | 303.6 t/s pp64 ≈ 3.3 ms/token |
| 0.6B decode | 23.8 tok/s | — | **46.4 tok/s** | 53.4 |

结论性的分工：

* **算力型（prefill、大 M）→ cblas**，80.9 GFLOP/s，是我们 RVV GEMM 的 2.8 倍；
* **内存型（decode、M=1）→ IME2 + Q4**，有效带宽约 2 倍；
* RVV 自研内核的价值在于"没有 BLAS/IME2 时的兜底 + 可移植性"，不在绝对峰值。

## 五、本次落地到仓库的改动

| 文件 | 作用 |
|---|---|
| `tilelang/riscv/llm/engine.py` | `Meta.layout`；`_gemv_name()` 按 blob 布局选 GEMV；ime2q4 关闭批量预填；init 时按 `IME2_BRIDGE` 预加载桥接库 |
| `src/tl_templates/riscv/llm.h` | `tl_riscv_gemv_q4_ime2()`：与 `tl_riscv_gemv_q8` 同签名的薄封装 |
| `tools/riscv_llm/make_q4_blob.py` | Q4_0 GGUF → IME2 tile blob |
| `tools/riscv_llm/make_q4_blob_hf.py` | HF safetensors → 现量化 + 重排（支持 bias、KV 补零、无 qk_norm） |
| `testing/riscv/ime/bench_q4_ime2.c` | 上表的逐算子 microbench |
| `testing/riscv/gemm/cblas_bench.c` | cblas 线程数实验（80.9 vs 34.9） |

许可证：桥接文件来自 mahiru 分支（Apache-2.0），其依赖的 spert / ime_kernels 为
SpacemiT MIT，Q4_0 量化规则引自 ggml（MIT，仅 12 行算术，非拷贝代码）；均已注明来源。

## 六、复现

```
# 1) 桥接库（vendor 内核 + spert）
bash /tmp/build_bridge.sh                      # 产出 libime2bridge.so

# 2) 权重（二选一）
python tools/riscv_llm/make_q4_blob.py    qwen3_06b_q4_0.gguf out.bin
python tools/riscv_llm/make_q4_blob_hf.py deepseek_r1_15b_hf  ds15b.bin

# 3) 跑
IME2_BRIDGE=/path/libime2bridge.so OMP_NUM_THREADS=7 PYTHONPATH=$PWD \
  python tools/riscv_llm/run_model.py out.bin tokenizer.json \
  --prompt "The capital of France is" --n 32 --maxseq 128 --raw

# 4) 逐算子
g++ -O3 -march=rv64gcv -o bq4 testing/riscv/ime/bench_q4_ime2.c -lime2bridge
./bq4 4096 1024 4 40
OPENBLAS_NUM_THREADS=4 ./cb 512 10
```

## 七、下一步（按收益排序）

1. **prefill 也上 IME2**（M=8/16 的 i8i4 GEMM）。0.6B 现在 prefill 25 ms/token，
   llama.cpp 只要 3.3 ms/token，这里是最大的一块空白。
2. **整图单 launch**：mahiru 证明 launch 不是瓶颈，但把 28 层放进一个 spert 图
   可以把中间结果留在 TCM，省掉 28 次全局内存往返。
3. **sampling 用 IME2 并行 argmax/top-k**：现在 head 4 ms 里 argmax 是标量。
4. karen 的整树构建与 IME2 ABI 对照，需要一次数小时的编译窗口。
