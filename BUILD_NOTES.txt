TileLang v0.1.15 RISC-V build notes (K3)

1. 3rdparty/tvm source: TileLang/tvm @ 4211874e (tarball), tvm-ffi @ 3c35034f, dlpack @ 84d107bf.
2. 3rdparty/tvm/cmake/config.cmake: TVM_FFI_USE_LIBBACKTRACE OFF (no network for libbacktrace download).

4. python tvm_ffi.core built manually (core.abi3.so) with a stub TVMFFITestingDummyTarget; TVM_FFI_BUILD_PYTHON_MODULE target is not generated by this CMake graph.

6. Baseline: python3 baseline_add.py -> PASS (max_err 0.0), target llvm/riscv64-unknown-linux-gnu, mattr +m,+a,+f,+d.
7. baseline_rv64gc.py (GEMM) fails in LayoutInference: fragment C_l layout cannot be inferred on the CPU pipeline (backend gap, next work item).

8. Pure RV64GC GEMM baseline (64x64x64, global-memory loops, no T.gemm): PASS, max_abs_err=0.0, 0.467 ms, 1.123 GFLOPS.
9. objdump of the cached kernel: 0 vsetvli, scalar flw/fsd only -> RVV is off as intended.

10. Step 2 first prototype: TileLang prim_func calling cblas_sgemm via T.call_extern (T.import_source + ctypes RTLD_GLOBAL preload). 512^3 f32: 3.519 ms, 76.28 GFLOPS, max_abs_err=0.0 (PASS).
11. OpenBLAS reference on X100 (numpy, 4 threads): 256^3 64.3, 512^3 71.2, 1024^3 72.3 GFLOPS. Scalar TileLang baseline was 1.12 GFLOPS.
12. Note: this is an extern-call prototype; T.gemm still has no RISC-V CPU lowering. Next: lower T.gemm to cblas for llvm target, then RVV codegen.

13. Added tilelang.language.gemm_cblas(A,B,C,M,N,K): row-major f32 GEMM via cblas_sgemm, exported through tilelang.language. Intent: give the RISC-V/CPU target a usable GEMM primitive while tl.gemm CPU lowering is incomplete (fragment layout inference + multiple dyn shared alloc gaps). Host must preload libopenblas with RTLD_GLOBAL. Test: bench/riscv_gemm.py, 512^3, 3.943 ms / 68.08 GFLOPS, max_abs_err=0.0. References: OpenBLAS CBLAS API (BSD-3-Clause), TileLang MIT; no third-party code copied, only a public C API call.

14. RVV codegen check: bench/rvv_add.py compiled with mattr +v emits vle32.v, vfadd.vv and vsetvli in the generated module (objdump on cached executable.so). N=4M f32 add: vec=1 5.718 ms (8.80 GB/s), vec=4 6.302 (7.99), vec=8 6.429 (7.83); all PASS. Add is bandwidth-bound on X100 (~9-10 GB/s measured), so vectorization does not help this kernel; RVV compute benefit is demonstrated by OpenBLAS GEMM (68 GFLOPS) instead.

15. Step 3 prototype: riscv/ime2_bridge.cpp exposes ime2_repack_q4 and ime2_gemv_q4 over C ABI (Spert stream inside, 4 A100 workers, IME2 gemm_kernel_i8i4). Built as libime2bridge.so linking ime2_kernels.o/rvv_kernels.o/repack.o + libspert + libggml. TileLang kernel calls it via T.call_extern after ctypes RTLD_GLOBAL preload. Correctness: random Q4_0 1024x1024 vs dequant reference rel=5.58e-03 (PASS). Perf: TileLang call 0.098 ms (6.01 GB/s), direct ctypes 0.110 ms (5.37 GB/s).

16. RISC-V ABI fix for the llvm target. Root cause: tilelang.compile with a bare llvm target picked host target "llvm" (soft-float), so generated modules referenced __addsf3/__mulsf3 (link error) or crashed at call time (SIGSEGV). Fix: tilelang/backend/target.py registers riscv-llvm-abi normalizer adding +m,+a,+f,+d for riscv64 (also on the auto/current-target path); tilelang/backend/module.py derives target_host from the riscv64 device target (same triple/mattr) instead of bare llvm. Regression: cpu suite 9 files / 88 tests all pass (previously bf16 test SIGSEGV); llvm suite 17 pass / 1 fail (f16 gemm produces wrong values; f32 gemm passes).

17. f16 fix: riscv64 LLVM needs +zfh/+zvfh. Without them, half arithmetic produced NaN (llvm gemm f16 failed). Added _riscv_host_half_features() in backend/target.py: parse /proc/cpuinfo isa (underscore-separated) and add +zfh/+zvfh only when the host advertises them; module.py uses the same helper for target_host. Final regression on K3: cpu 9 files / 88 tests pass; llvm 5 files / 18 tests pass; 0 failures.

18. Model-level block: bench/qwen_ffn_tilelang.py assembles a Qwen3-0.6B FFN (hidden 1024, ffn 3072) from TileLang kernels: two cblas GEMMs (gate/up, down) + one T.Parallel silu-mul kernel. rel_err=0.0 vs torch for m=1/8/32. Timing: m=1 7.445 ms (2.54 GFLOPS), m=8 11.230 ms (13.45), m=32 19.069 ms (31.67). Decode m=1 is memory-bound and OpenBLAS GEMV is inefficient; prefill is compute-bound. Next: quantized GEMV via IME2 for decode, OpenBLAS only for prefill.

19. Decode FFN via IME2: bench/qwen_ffn_ime2.py builds Qwen3-0.6B FFN (hidden 1024, ffn 3072) from three ime2_gemv_q4 calls + TileLang silu kernel. rel_err=9.284e-03 (PASS). 0.681 ms/token vs OpenBLAS m=1 7.445 ms -> 10.9x. 28 layers extrapolate ~19 ms, competitive with llama.cpp 37 tok/s. Bridge fix: qa buffer now reallocates when K grows (previous static alloc overflowed for the 3072-wide down GEMV).

20. lm_head-scale IME2 GEMV: bench/lmhead_ime2.py, N=151936 K=1024 Q4_0 (87.5 MB). repack 0.26 s; GEMV 4.649 ms = 18.82 GB/s (A100 streaming peak ~18 GB/s). Decode budget so far: FFN 0.681*28=19.1 ms + lm_head 4.65 ms = 23.8 ms -> ~42 tok/s before attention/norm/sampling, i.e. already at llama.cpp 37 tok/s territory.

21. Full IME2 decode budget (direct ctypes, 4 workers, weights warm): q 0.104, k 0.060, v 0.059, o 0.098, gate 0.127, up 0.126, down 0.129 ms -> 0.703 ms/layer; lm_head 4.319 ms (20.3 GB/s). 28 layers 19.68 ms + lm_head = 24.00 ms -> 41.7 tok/s before attention/norm/sampling (llama.cpp reference 37 tok/s). w8 streams are invalid on this runtime (launch returns -1), only 2/4 workers usable; 4 is best.

22. GQA attention moved into the bridge (qwen_attn_fwd): scores cached once, 4-thread OpenMP over heads, -O3 -ffast-math. seq=128 0.124 ms, 512 0.369 ms, 1024 1.128 ms; rel_err 3.8e-07/8.3e-07/1.2e-06 vs torch. 8 threads was much worse at small seq (1.9 ms) due to per-call OpenMP overhead; 4 is the sweet spot. TileLang-only 3-kernel attention was 1.08-1.19 ms at seq 128 (correct but slow), kept in bench/attention_tilelang.py as reference.

23. End-to-end decode (random Q4_0 weights, same shapes/ops): qwen_layer_fwd chains rmsnorm + 7 IME2 GEMVs + qk-norm/rope + attention + residuals. 28 layers + lm_head: 32 tokens in 1352 ms = 23.7 tok/s (42.25 ms/token). Single layer alone 1.174 ms vs component sum 0.827 ms; the gap (~0.35 ms) is 7 Spert launch overheads (~0.05 ms each). llama.cpp references: CPU 29.5 tok/s, SPACEMIT 36.99. Next: fuse qkv and gate/up into single launches, or move whole model into one Spert graph like the vendor backend.

24. Launch-merge experiment: ime2_gemv_multi fuses qkv (3 gemms) and gate/up (2 gemms) into one Spert launch each. Result: layer 1.28 ms / 22.8 tok/s vs 1.174-1.208 ms / 23.7 tok/s for separate launches — no gain, within run-to-run noise (+/-10% on this board). Reverted to per-GEMV calls. Conclusion: per-worker serialization means fusion does not reduce the critical path; the only remaining lever is one Spert graph for the whole model (vendor backend approach), not fewer host launches.

25. Whole-model single launch: riscv/qwen_graph.cpp runs all 28 layers + final norm + lm_head + argmax inside ONE spert launch (4 workers, ctx->sync between phases, 6 barriers/layer). 32 tokens: 738.9 ms = 43.3 tok/s (22.6-23.1 ms/token), above llama.cpp SPACEMIT 36.99 and CPU 29.5. Correctness: same weights/inputs vs 28 sequential qwen_layer_fwd calls, max_abs_diff 3.58 on values ~14500 (rel 2.3e-4, f32 accumulation-order differences). Caveats: random Q4_0 weights (same shapes/ops), final norm reuses an[0] instead of a separate model.norm weight, argmax sampling only.

The capital of the United States is". 348.4 ms for 16 tokens = 45.9 tok/s. Critical bug fixed: KV cache was shared across all 28 layers, so from the second token on, attention read K/V overwritten by the last layer. KC/VC are now (NL, NKV, MAXT, HD).
